## Plain-language overview

Wildstone already acts as a manager: Keystone records what the homelab should look like, and Wardstone performs specific actions on each enrolled machine. For example, installing an application creates declarations for its container, configuration and storage; Wildstone then tries to make the machine match those declarations.

The main questions concern trust in that process. If a person edits a declaration while another change is being approved, which exact version is allowed to run? If you approve a container update on host A, can unrelated risky drift on host B also be repaired during that tick? The audited code exposes boundaries that need review; the failure scenarios are inferred, not reproduced incidents.

Optional tools would cover separate jobs: OpenTofu could create a VM, Ansible could prepare Linux and Docker on it, and Wildstone would continue managing applications through Wardstone. Ordinary users could keep providing their own host and running the existing installer. Backups preserve data, while recovery tests must also establish that restored services start with the right configuration and identity.

Discussion draft: strengthen the existing control plane before adding infrastructure automation.

## 1. Scope, evidence, and conclusion

**Wildstone already implements a meaningful declarative control plane.** Git-backed resources, package expansion, policy checks, risk-graded Plans, typed host execution, continuous reconciliation and Restic recovery are implemented. This is not an imperative installer that needs a complete IaC replacement. The primary gaps are the consistency and authority boundaries between desired state, approvals, observed reality, host prerequisites and recovery activation.

This was a read-only static implementation audit. The complete recursive tree (2,111 entries, not truncated) was inventoried, and 134 relevant source, workflow, package, documentation and test files were retrieved at the pinned commit. Representative regression tests were read, not executed. No repository code, issue or PR was changed. No production host, Proxmox server, storage export or credential was accessed.

Verified means behavior directly visible in implementation/wiring. Inference means a consequence of that implementation that was not reproduced here. Recommendation means a proposed future boundary; it does not supersede accepted ADRs.

## 3. Sources of truth and workflows

### Sources of truth

| Fact | Authoritative source | Derived / external counterpart |
| --- | --- | --- |

| Host foundation | Installed OS/packages, systemd/env files, operator settings, hypervisor/NAS configuration | Mostly outside the Statefile; installer answer persistence is a resume mechanism, not a complete infrastructure specification. |

### Install and deployment

1. Operator provides a Linux host with systemd and supported architecture. The interactive installer can install Docker/Tailscale using upstream scripts; noninteractive node installation expects Docker unless explicitly skipped.
2. Installer downloads a selected release or uses local artifacts, checks SHA-256 sums, installs binaries/catalog/UI and systemd units, and preserves selected configuration on rerun.
3. Wardstone enrolls with a join token and optional CA fingerprint. A node is not created as a VM by this workflow.
4. A capability request expands package parameters/traits into resource YAML, validates policy and creates a stored proposal. Proposal diff is desired-vs-current-Statefile, not an exact live execution plan.
5. Approval checks the base Git HEAD, writes resources/deletions, commits Git, advances the DB marker, then transitions the Plan to approved.
6. The reconcile loop loads current resource files, projects DB facts, observes per node, recomputes an execution diff, applies typed operations, checks postconditions and records results.

### Updates and drift

Application images are digest-pinned. Package version/content locking and image refresh tooling exist. RefreshDigests uses an OCI resolver for “latest” manifests; release selector/version-set behavior must be checked before treating refresh as a safe automated update. Container replacement stops/removes the old container before creating its replacement.

Out-of-band Git edits are detected by HEAD versus the DB marker. Subsequent edits are schema/policy-validated and recorded as auto-approved system/oob Plans; invalid edits are reverted with a new commit. Initial adoption only calls State.Load and advances the marker, without the normal Policy.Validate call. Reconciliation also reads working files, so uncommitted valid edits can enter its input independently of HEAD ingestion.

### Recovery

BackupEngine schedules Restic runs, treats incomplete snapshot exit codes as errors, handles capacity/mount checks, and supports local-and-offsite or offsite-only routes. Database hooks include PostgreSQL custom dumps and SQLite backup helpers. Whole-site recovery exports Git, SQLite and sealed household/node secrets; restore regenerates trust identities and starts under quarantine. Offline nodes can reuse a previous sealed node bundle, so freshness is not uniform across a multi-node snapshot.

The original exit drill preserves a Statefile copy and the backup repository while deleting host/app state. The newer S3-only drill destroys local state and recovers from a kit plus external S3 server. Neither provisions a replacement OS, VM, NAS or tailnet. App restore is generally alongside first; moving data/dumps into active services and verifying logins/device identities remains package-specific.

## 5. Recommended target architecture and tool responsibilities

**Keep Keystone as the central authority and user experience.** Keep its resource vocabulary, policy/proposal pipeline, agent grants, Wardstone transport and existing backup engine. Introduce mature tools where capabilities are absent, with one writer per managed object.

| Component | Owns | Must not independently own |
| --- | --- | --- |
| Keystone | Accepted intent revisions; policy/risk review; resource ownership; plans/results; node enrollment; controlled orchestration | Reimplement all hypervisor/cloud APIs or arbitrary agent-authored execution. |
| Wardstone + current Docker runtime | Bounded ongoing node operations; workloads/config/routes/secrets/mounts assigned to it; live observations | General unrestricted shell or competing host-baseline mutation. |
| Optional Ansible profile | Host baseline: selected OS packages, Docker/Tailscale installation, systemd configuration, kernel/sysctl/BlueZ prerequisites; predictable install/upgrade inputs | Wildstone-owned containers, routes, NFS entries and service configs. Initially run explicitly from an operator machine; integrated execution comes later. |
| Optional OpenTofu profile | Provider-owned VM lifecycle, sizing, virtual disks/NICs, templates/cloud-init and infrastructure outputs | Wildstone application resources; direct modification of an already-enrolled host's service configuration. |
| Current capability packages | Validated typed service intent and connection contracts | A parallel Compose lifecycle controlling the same containers. |
| Restic + existing BackupEngine | Selected data protection, retention, checks, restore records and whole-site recovery | Hypervisor provisioning or assumptions that bytes restored equals service/device identity restored. |
| Existing monitoring/notifications | External metrics storage/visualization and alert delivery | A replacement desired-state store or a second repair engine. |
| Agents | Read observed evidence, propose bounded changes, use explicitly granted operational tools | Approval of their own infrastructure proposal or unrestricted hypervisor/SSH credentials. |

### The interface contract

For optional execution backends, define a versioned InfrastructureRun envelope with backend/workspace identity, input commit/digest, accepted desired revision, target IDs, dependency/output schema, plan artifact digest, risk/action bounds, scoped credential references, preconditions, timeout and idempotency key. Return a durable result with backend state serial, actual changes, uncertainty, errors and rollback/recovery requirements. Extend existing Plan/status records rather than building a second approval product.

An OpenTofu workspace is a stateful unit of planning/execution. Protect its state with locking, preserve a saved plan artifact for approval, and invalidate it on changed inputs/state. Local locked state on a durable executor is sufficient for one writer initially; add a locking remote backend when multiple writers require it. Protect plans/state as sensitive artifacts. Do not host the only recovery copy or only executor credentials on the VM that the same workspace destroys.

Ansible check/diff is useful preview evidence, but it is a simulation with module/conditional limitations, not a cryptographically exact saved execution plan. Limit execution to pinned, reviewed roles with explicit inputs; recheck relevant host facts. Do not allow model-generated playbooks or arbitrary command overrides through the runner.

### Compose and orchestration alternatives

Docker Compose is a sensible production tool for independent single-host applications. Here, replacing the current typed Docker reconciler with Compose would be a large ownership/security migration. Compose imports can eventually be compiled into a supported subset of typed resources and rejected on unsupported fields, with no second runtime writer. A read-only export is lower-risk. Swarm, Nomad or Kubernetes become relevant only when measured requirements demand cluster placement/failover/rolling deployment; multiple static nodes alone do not justify them.

> **Later direction (2026-10-24):** [ADR-W050](../../decisions/ADR-W050-multi-node-runtime-kubernetes-engine-host-providers-editions.md) (proposed) records that requirement: the household goal is placement, failover and rolling updates across 1 to N machines, so it proposes k3s behind Wardstone, with Ansible as the Linux-edition host layer. This audit's findings are otherwise unchanged.

### Host and provider options

Ordinary users keep “bring a host, run the installer, install capabilities.” Advanced users can first run reviewed Ansible roles to prepare that host. Later, OpenTofu provisions a Proxmox VM, returns a versioned inventory, then Ansible prepares it and Wardstone enrolls. Imported existing VMs require a read-only/no-change import verification before taking lifecycle ownership. NAS pools, physical switches and hypervisor cluster/HA remain externally administered in the first increment.

Primary references: [OpenTofu state locking](https://opentofu.org/docs/language/state/locking/); [saved plans and sensitive artifacts](https://opentofu.org/docs/v1.11/cli/commands/plan/); [local backend locking](https://opentofu.org/docs/v1.10/language/settings/backends/local/); [Ansible check/diff limitations](https://docs.ansible.com/projects/ansible/latest/playbook_guide/playbooks_checkmode.html); [Compose production scope](https://docs.docker.com/compose/how-tos/production/); [OpenGitOps principles](https://opengitops.dev/). Tool choices and boundary assignments above are recommendations, not claims made by these sources.

## 8. Reliability verdict and discussion decisions

**Can Wildstone reproduce an installation today?** It can reconstruct declared workload shape and restore protected data under documented prerequisites. The code and CI show a substantially stronger recovery foundation than a typical shell/Compose homelab. The inspected evidence does not establish fully reproducible physical/VM infrastructure, a pristine OS-to-working-household install at this SHA, coherent arbitrary multi-node snapshots, automatic service activation, or uniform drift/rollback guarantees.

**The highest-leverage first work is G1 and G2.** A saved OpenTofu plan, an Ansible preview and a new provider all depend on reliable publication and bounded authorization. Add those tools after stabilizing those guarantees; otherwise they multiply the same ambiguity across more powerful backends.

Discussion should settle three boundaries: (1) the accepted immutable revision is the only infrastructure reconcile input, with DB projections tied to a recorded generation; (2) approval permits explicitly bounded effects even when live diffs change; (3) host/VM automation stays optional, while everyday users retain the existing installer and capability workflow. Runtime implementation has not been authorized or started by this audit; the subsequent authorization covers this document and tracker only.
