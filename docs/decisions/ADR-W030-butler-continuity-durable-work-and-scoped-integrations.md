# ADR-W030: Butler continuity, durable work, and scoped integrations

- **Status:** accepted and largely implemented (Part C, P1–P16).
- **Governed by:** ADR-W033 where they overlap.
- **Relates to:** ADR-W004 (Plans), W005/W025 (packages and integrations), W006/W017 (Butler), W007 (Keystone), W009 (policy), W012 (secrets), W020 (identity), W024 (household automation), W026 (messaging), W027 (conversation UX), W028 (failure isolation).
- **Source:** household-owner design discussion, consolidated in [the capability and design brief](../butler-capability-and-design-brief.md).
- **Baseline:** main at `2e45b0db21ec644fc13c0cb10dc094e4c1408e12`.
- **Audience:** architecture review. Part A is binding; Part C is the ordered implementation plan and its recorded evidence, and may be refined without weakening Part A.

## Intent and problem

One Butler should remember relevant context, complete work over time, and coordinate applications, while the Agent and Connection through which a Person speaks remain firm authority boundaries.

Wildstone already has a deterministic household engine, an event timeline, approved Automation resources, domestic executors, provider abstraction, audited conversations, and chat bindings. W024 already incorporates the earlier agent architecture summary. This ADR extends that foundation rather than introducing another event bus or a replacement automation engine.

Current chat continuity is not a restart-safe task system. A package declaring an agent tool is not enough to supply and authorize its executor. Transport-bound histories do not let a conversation follow the Person across Connections. Learned memory, tool requests, and cross-app work need lifecycle and authority contracts before implementation expands them.

The current catalog includes a Roundcube mail/calendar client package. Installing that client does not establish Butler's mailbox access, CalDAV retrieval, calendar writes, or ingestion permissions.

# Part A — Decisions

## A1. Household-owned Agents, two classes, explicit sessions

The household runs one or more household-owned Agents (Butlers) in two classes, Owner and Member (ADR-W033 B1, B2). A Member Person reaches only Member Agents; an Owner Person may reach either. Member Agents offer scoped household knowledge and permitted app actions. Owner Agents add administrative tools; host-state changes remain human-approved Plans, and no approve capability or arbitrary host shell is added. A child is a constrained Member profile, not a separate Agent or surface; a child acting remains gated by A2.1.

Homepage or app access does not grant Agent admission. Adults admitted to the household have equal shared-memory standing; personal privacy, Owner authority, and guardian relationships remain separate concerns. Do not build a role hierarchy beyond Owner and Member.

Shared household routines are household-owned (W033 E5). Members and Agents may propose creating, changing, or disabling one without the original author's permission; only a human Owner approves the exact version, and every edit needs reapproval (W033 E2–E4). Any Owner may stop a routine immediately without a Plan (W033 E6.1). Any admitted adult may correct or forget household-shared memory without approval from the original author. Preserve author, last editor, version, and audit history, and notify the routine's proposer of another Person's behavioral change. Corrections and forgets of household-shared memory are audited and appear in the next configured learning digest for the other admitted adults; removal of a safety-relevant record also produces an immediate notice. Personal memory is controlled by the Person it describes; an Owner's administration of the server is not ownership and grants no authority to widen or promote it (W033 C4, C7). Safety-relevant records such as allergies show their source and scope rather than disappearing silently.

The Agent a Person addresses sets the execution boundary: a Member Agent cannot invoke Owner tools, even for an Owner. A session is Person + Agent + session id (W033 B10); continuing with the same Agent on another Connection continues the eligible session. Talking to a different Agent is a different session; continuity across Agents comes from Personal and Household memory (W033 C5), never from carrying one Agent's context into another, and never executes a pending operation.

_Changed by ADR-W033 §B1, B2, B10, E2–E6.1: surfaces became household-owned Agents with Connections, and routine activation became Owner-only._

## A2. Shared history does not mean shared disclosure

Conversations are sessions keyed by Person + Agent + session id. A message on another Connection continues the eligible session within the recency threshold, asks when several are eligible, and starts a new session otherwise; candidates are filtered by the current Connection's disclosure policy (W033 B10). Explicit references can resume an earlier session.

Retrieval is constrained by the authenticated Person, the Agent, the Connection, and the audience before content reaches the model. Shared storage must not expose adult-private or Owner-Agent information through Member-Agent or group sessions. Summaries, cached context, and learned procedures inherit the restrictions of their sources. Do not reuse a previously constructed privileged model context across a boundary change.

Keep named app-account mappings to one Wildstone identity. The model cannot assert acting identity. Shared app credentials retain the requesting person's attribution.

### A2.1 Identity admission and audience defaults

Maintain an explicit runtime link between an authenticated surface identity and a household member; API principals, chat bindings, and trusted-ingress identities are named link types, and equal names are not proof of identity. A link is established by authenticated enrolment, where the Person collects their own single-use key (W033 A2, B7.1), or by direct Owner administration in Console/CLI; its runtime projection supplies dispatch checks. Butler cannot grant itself manage authority. Keep original surface/member attribution immutable in history; do not reinterpret old authorship when a link changes.

Agent admission and guardian/classification changes are direct Owner administration; admission is ordinary rather than consequential (W033 A4.1). An unlinked surface identity has no household-person access. Butler admission and disabled status are runtime membership controls, separate from LDAP account deletion or group membership. Check current membership and link generation at every retrieval and dispatch. Unlink or disable revokes derived authority immediately, and affected work stops at its next boundary (W033 F1); relinking requires fresh authorization. Admission to a Member Agent does not admit a Person to an Owner Agent.

Offboarding starts with one audited Owner action that immediately disables Agent admission, revokes chat bindings, sessions, and Person-bound approvals, fences the Person's integration connections, and prevents new retrieval, dispatch, ingestion, and proactive delivery. Durable resources are then resolved through the W033 F2 inventory; failed cleanup never restores access. A sole guardian cannot be removed while a Child admission remains active: assign another guardian or disable the Child admission first.

In direct messages, an admitted Person sees shared household timeline records whose audience includes them, including other Persons' household events (W033 C7). Explicitly private sources remain restricted. Group destinations follow W033 B9/B9.1: only messages addressed to the bot reach the Agent, Owner Agents answer in direct messages only, and a group audience does not inherit the sender's direct-message access.

For the existing household timeline, registered legacy event types retain their household-shared audience under an explicit migration mapping; no blanket historical relabeling is required. That mapping also explicitly includes Keystone-owned automation lifecycle events and household-answer events from the existing chat/notification paths, which are not package-declared. Recognize trusted producer paths and event types together; a caller-supplied internal source name is not proof of origin. Extend package `publishes` declarations with audience policy: household-shared by default for declared household events, or a narrower validated audience. Persist the resolved policy/provenance at intake and preserve subsequent access revocations. Unknown event types, invalid audience declarations, imported personal sources, and missing derivative permission metadata fail closed. Derivatives of legacy events inherit the mapped audience. The timeline is not a general exemption from permission checks.

A future Child surface requires its own bot credentials, principal/role, endpoint, structurally limited gateway, and boundary tests. Guardian mappings and child classification are explicit admission records, never inferred from an LDAP group. Transport eligibility must be checked before enabling that future surface; no child deployment is authorized here.

## A3. Memory is owned data with derived retrieval indexes

Use one logical household memory service, structured records for exact facts and permissions, and hybrid meaning/keyword retrieval for selected text. Application records remain authoritative for current app state; live reads verify changing facts when needed. A vector database product is not selected here.

Butler may learn preferences and reusable procedures automatically. Distinguish explicit statements from tentative inferences; retain source, date, and corrections. Explicit preferences persist until corrected or time-bounded; unused inferences lose influence. Learned procedures confer no permissions and do not enable routines.

Offer configurable daily/weekly learning digests and inspect/correct/forget controls. The digest includes another Person's corrections and forgets of household-shared memory; safety-relevant removals do not wait for the digest. A private source does not become household knowledge through extraction. Query permission does not imply bulk indexing permission.

Deletion removes retrieval access and solely dependent derivatives; forgetting prevents relearning from the same historical material. Original records survive compaction unless separately deleted. Forgetting and deletion are journalled so a restore cannot resurrect them (W033 C10), and the restore quarantine in A10 is required.

While admitted, a person can export their own conversations, personal memory, preference/procedure records, and task history in documented machine-readable form. The export includes provenance and permissions but no other person's private data, credentials, hidden Owner-Agent context, or shared data the requester cannot currently read. On offboarding, personal conversations and memory become inaccessible rather than becoming household-shared. They remain quarantined until an Owner resolves them through the W033 F2 inventory, the configured retention period expires, or an authorized deletion request completes; without an explicit period, the existing manual-deletion default applies. Shared household facts remain with original attribution.

### A3.1 Memory acceptance boundaries

Use the shared redaction path before persistent memory storage, including exclusion of credentials and password-reset material. Source restrictions apply before extraction and persist on every derivative. When sources have different restrictions, a derivative must satisfy all of them; missing permission metadata fails closed.

Test poisoned inferences, malicious learned procedures, and attempted private-to-household extraction as distinct cases. An inference never becomes authorization; a learned procedure never bypasses current tools or approvals. Attribute a group statement such as “I dislike cilantro” to the authenticated sender, with its source audience recorded separately; it is not a preference of everyone in the group.

## A4. Tasks and routine runs share durable execution machinery

**Implementation reconciliation (slice 24, #225).** The conversational Task is
the durable `conversation_work` parent introduced in slice 21 (#222); each
turn retains its own `butler_tasks` ledger and evidence. The parent carries
the aggregate tool-call budget and unresolved external outcome into later
turns. `TestConversationParentCarriesBudgetAcrossTurnLedgers` and
`TestConversationParentPreservesUncertainOutcome` exercise those boundaries.
The stored per-turn state machine has no separate `partially-completed`
state: completed steps and receipts remain in the ledger, while an unmet
objective remains waiting or fails. Reporting must name completed effects
and remaining work from that evidence, never mark the whole objective
complete because one effect succeeded. `TestEveryRequiredEffectNeedsMatchingEvidence`
enforces that completion boundary. The broader runtime/deadline/cost budgets
described below remain design requirements; this reconciliation does not
claim they are all implemented.

Use one execution foundation in Keystone for conversational tasks and Wildstone-owned routine runs. Retain routine definitions separately from each occurrence. Model-free steps remain model-free; agent steps receive bounded context and grants.

Recommended starting point: runtime-DB task/run rows, step/attempt rows, and transition history. Record Person, Agent, session, objective, completion criteria, grants, deadline, next wakeup, results, and uncertainty. Exact schemas, claim/lease design, and migration are deferred to an implementation specification.

Replies, approvals, schedules, and unavailable models are saved waiting reasons. Cancellation stops new actions and attempts to interrupt in-flight work. Refinements preserve task history; separate objectives create separate tasks. Independent work may run together; incompatible shared changes pause for clarification rather than assigning one adult priority.

Offboarding moves the Person's unfinished personal tasks to `paused-offboarded`; they perform no retries, notices, or model calls, and are exported or deleted through the W033 F2 inventory. Household routines and shared work continue with original authorship preserved; only a routine that delivers to the departed Person or depends on an admission only they held pauses for Owner resolution (W033 F1). Task retention then follows the same configured offboarding policy as its conversation.

Resume relevant authorized work after restart. Do not blindly retry actions whose outcomes are unknown. Use destination verification or supported idempotency mechanisms; otherwise pause. Preserve partial successes and report remaining work. Completion requires evidence appropriate to the objective, not merely a model saying done. Notification delivery is separate from task completion.

This does not claim exactly-once external execution. The W024 timeline remains authoritative for deterministic automation decisions and outcomes; task rows own agent steps, waits, attempts, and completion evidence. Link records by occurrence/action IDs and treat copied status as a projection, not a second authoritative result. Deterministic timeline replay must still work with an empty task table. Existing `automation.acted` records represent dispatch claims, not proof of successful external effects; migration must preserve that distinction.

Checkpoint each tool invocation before dispatch and after its result. Resume from the validated step ledger, reconstructing context with current permissions, rather than replaying a saved model/tool transcript. Persist model-call, tool-call, and active-work budgets across restarts. Exhausted budgets wait for review; they do not reset on retry. Waiting does not consume active-work budget, while absolute deadlines still expire.

Expose per-Agent-class interactive iteration limits as validated runtime configuration in Console/API using the W017 A9 pattern. Initial configurable defaults are 16 rounds for Member Agents and 24 for Owner Agents, subject to implementation evaluation; count individual tool calls separately because one model round can request several. Snapshot limits onto the task. A turn reaching its slice limit checkpoints and waits to continue without discarding evidence or resetting aggregate task budgets. An authenticated “continue” resumes the unambiguous originating task; otherwise ask which task. Continuation grants another bounded slice only within the existing total budget, never action approval or extra authority. Exhausted total budgets require explicit review of a bounded extension.

Provider failures and stalls retain the same resumable ledger as restarts. Enforce a configurable provider-stall deadline, cancel/fence the abandoned attempt, and reject late results from superseded attempts. Retry, or fall back along the Agent's own ordered model chain (W033 B6), within remaining budgets before involving the person. If still blocked, send a deduplicated notice on the originating Connection with a task-bound continue control/text path, respecting notification policy. The P4 minimum sends only to the task owner's originating direct Connection, reuses the existing outbound deduplication key, and holds non-urgent stalled-task notices during the household-timezone quiet hours; P15 adds per-person overrides, broader routing, relevance, urgent exceptions, and reply correlation. Console distinguishes stalled/resumable work from terminal failure. Refresh stale observations on resume; do not repeat already-verified effects.

## A5. Common contracts, application-specific adapters, named integration connections

In this ADR a *connection* is an integration connection to an application (CalDAV, Home Assistant). A *Connection* in the W033 B7 sense is how a Person reaches an Agent.

An integration declares events it reports, queries it answers, and actions it performs. Capabilities can be partial. Responses distinguish valid results, including empty lists, from unavailable/stale information and carry source and observation time.

Application-specific code belongs in adapters outside Keystone; native publishers need no additional publishing process. Support both packages integrating Wildstone-managed apps and connection-only packages for externally hosted apps. Connecting does not take ownership of the remote application. Adapters may run on a managed machine that can reach the app, not necessarily the app's host.

An adapter implementation supports multiple named integration connections, each with endpoint, credential references, identity mapping, and grants. Credentials follow the secret path and never enter model context.

Each connection declares one primary adapter node and an ordered, explicitly approved set of eligible fallback nodes. The approving placement Plan deploys and starts the adapter container and provisions required connection secrets on every listed node before that node becomes eligible. One lease epoch permits only the current holder to claim work; the other running containers remain ready but inactive. Keystone may automatically move only that lease within the prepared set when the primary is unavailable. It never creates a container, selects an undeclared node, or copies credentials during an outage. Stale adapters/results from an earlier epoch are fenced. Automatic failback waits for a configurable healthy stabilization period to avoid flapping. When no eligible node is available, dependent work waits and Butler reports the outage.

Connection defaults follow ownership. An individual account starts personal, read-only, live-query-only, and local-processing-only until its owner explicitly widens indexing, audience, actions, or cloud use. A service explicitly connected as household infrastructure starts household-shared and read-only; selected RAG indexing is an explicit setup choice, and cloud processing still requires the record and source processing policy in A9.1. Discovered actions remain disabled until separately enabled and granted.

Verify available capabilities against app version, configuration, and granted access. Discovery does not authorize newly available permissions. Outages mark capabilities unavailable and dependent work waiting.

Keep event intake, on-demand queries, and optional RAG indexing distinct. Preserve the canonical household timeline and SQLite bus decision in W024. No new broker or log-parsing contract is selected.

### A5.1 Adapter transport and personal credentials

Reuse the long-poll/ack pattern of the existing chat outbound queue, with a separate durable integration-work queue and dedicated claim/result endpoints; do not overload `chat_outbound` or chat's inbound message path. A waiting poll wakes when work arrives; queries have explicit deadlines and return unavailable on timeout. Keystone needs no new inbound adapter-controlled administration surface and makes no app-specific outbound calls. Adapter principals can claim/report only work assigned to their named connections; they gain no general query, act, or manage authority. Versioned request/result envelopes carry correlation IDs and validated capability/scope metadata. Introduce the closed `integration-adapter` role with `claim-integration-work` and `report-integration-result` verbs, connection-bound by Keystone. This does not expand `emit` or `converse`. The interactive query deadline defaults to 5 seconds end-to-end, including queue delay, configurable within the caller's remaining budget. Exact endpoint and lease schemas remain implementation work.

V1 adapters execute as package-managed containers on Wildstone nodes that can reach the external app. Resolve secret references through the existing node secret path into the adapter's scoped environment; secret values never travel through work/result queues. Connection setup may fan one authenticated secret input directly over mTLS to the explicitly eligible Wardstone nodes without persisting it in Keystone. Adding a fallback is a Plan and is incomplete until the adapter container is running, its secret is provisioned, and readiness is verified. Removing one immediately fences its lease, stops and removes the adapter container so it cannot retain or rematerialize the credential, then verifies local secret erasure and, where the remote service permits separate credentials, revokes that node's credential. If container removal, erasure, or revocation cannot be proven, removal remains incomplete and the connection reports degraded. Connection-only describes ownership of the remote app, not an unmanaged adapter runtime. Running adapters on non-node machines requires a later credential/identity design.

The existing home-automation emitter is not a Home Assistant query/action adapter. Add that capability explicitly in an adapter with declared permissions, independently of whether Wildstone hosts Home Assistant.

Personal CalDAV/IMAP access requires member-scoped credential onboarding through an authenticated secret-input surface, following W020's claim/onboarding pattern and W012's secret handling. Store credentials through the node secret path; adapters receive scoped references, never model-visible values. Keep member, connection, requesting principal, and revocation linkage. Do not collect passwords through chat. Revocation invalidates future dispatch and ingestion. Where a provider cannot issue read-only credentials, enforce read-only adapter operations and disclose the credential's wider upstream power. Personal CalDAV rollout depends on this onboarding; fixtures can precede it.

Offboarding disables every personal connection and starts verified credential erasure/revocation on all eligible nodes. A household-shared connection whose credential belongs to the departing Person pauses for Owner resolution through the W033 F2 inventory; it cannot resume until an Owner supplies or reauthorizes a credential. Connection and routine history retain the departing member's original attribution.

### A5.2 Amendment (epic #326 S01): package-bundled adapters and node-bound claims

A package declares an adapter in `integrates:` (docs/catalog-integration-contract.md §4). The declaration is inert at install and upgrade: `capability.Engine.Expand` never reads it, so installing a package that bundles an adapter creates no adapter container, credential, connection or upstream read. The adapter is rendered only per connection placement by `capability.Engine.ExpandAdapter` — one container per prepared node, owned by `integration/<connection>` rather than by the capability so a package upgrade never reads it as leftovers — and it inherits named package params, the package version and the placement node, never a credential. V1 adapter programs are Wildstone binaries shipped by the release and installed on every node under `/srv/wildstone/bin`, run in a pinned public base image, like the chat adapter (W033 B7.1); the first is `wild-mail-adapter`.

The declaration fails closed on version skew rather than loading partially: an older Keystone rejects the unknown key under strict parsing, a newer adapter contract, unknown domain, unshipped program or undeclared query is a validation error, and the rendered container uses the protocol-minor-18 hardening fields so an older Wardstone is refused the step. Inside a declared integration domain the vocabulary is enforced at dispatch as well as declaration: the integration-work queue refuses a query or action name the domain does not declare, so a read-only domain (mail) cannot be sent an action even on a widened connection.

"One lease epoch permits only the current holder to claim work" is now enforced at the claim: an adapter principal may be bound to a placement node (migration 0097), and such a principal claims only while that node holds the lease and is not being removed. A principal bound without a node keeps the earlier connection-wide meaning.

### A5.3 Amendment (epic #326 S02): Personal credential intake, verified erasure, and unattended authorization

The Personal credential path A5.1 describes is now implemented end to end for mailbox app passwords.

- **Intake.** `POST /api/v1/integrations/{name}/credential` (Console/CLI) and `POST /api/v1/home/integrations/{name}/credential` (Homepage) take `{login, password}` from the connection's owning Person only. The value transits that request and one `PutSecret` per placement node over mTLS, and is kept nowhere in Keystone: no column can hold it (migration 0098), and it is absent from responses, events, the audit chain and logs. Node secret names are `pc.<connection>.v<version>`; Wardstone leaves the `pc.` prefix out of the household recovery bundle, since a Person re-enters their own credential after a recovery.
- **Lifecycle.** Each version is `staged` → `active` → `superseded`/`revoked` (or `failed`). Copies are recorded per node *before* the value is sent. Replacement stages the new version on every placement node before fencing the old; a staging that misses a node fails, leaves the working credential alone, and erases what arrived.
- **Fence, then erase.** Revocation (by the Person, an Owner administering, offboarding, or restore replay) moves the lease epoch, cancels queued and claimed work, revokes background authorizations and unprovisions placements in one transaction; only then are copies erased. Erasure is proven per copy by the Wardstone `EraseSecret` operation (protocol minor 22): version-fenced, idempotent, and answering with `absent` plus evidence `sha256("wardstone-erase-v1"‖name‖nonce‖version‖absent)` over a fresh nonce (`proto/secreterase`). A version that was ever active also needs its adapter container removed, since the container's environment holds it. Anything unproven — an unreachable node, an agent below minor 22, evidence that does not verify — leaves the connection `degraded` with reason `erasure_unverified: …` until `POST /api/v1/integrations/{name}/credential/erase` proves it. `ProvePlacementRemoval` no longer accepts a caller's "secret erased" for a node holding such a copy.
- **Restore.** A restored database stays quarantined, so no unattended use is possible before the journal replay. Replay re-fences journalled credential and authorization revocations, and the post-replay erase sweep also erases any `pc.<connection>.` name on a placement node that Keystone does not hold live — the version a snapshot never heard of.
- **Unattended use** requires the Person-authorized, Owner-approved intersection defined in ADR-W033 D1.1.

## A6. Native automation where appropriate, Wildstone for cross-app coordination

Butler authors native routines through supported app interfaces when that app owns the workflow. Wildstone executes cross-app routines using incoming events and targeted queries. Track external routine IDs and edits; do not silently duplicate or migrate execution.

The platform supplies schedules/events, conditions, uncertainty handling, repeat controls, typed actions, replies, preview, trial mode, versioning, and audit. Breakfast and appointment examples in the brief are acceptance scenarios, not hardcoded product features. Timing, destinations, eligibility, and missing-data choices belong to user-authored routines.

Preview without side effects where historical evidence permits; disclose unavailable historical context. Native routine creation, behavioral edits, and deletion use Plan-mediated declarations that record the connection, external ID, ownership, and approved behavior. Removing a connection or declaration does not silently delete an external routine. Wildstone-owned routines retain approved Automation resources.

Local disable immediately blocks further Wildstone dispatch. It cannot by itself stop a routine running inside another application. A native stop requires a supported, explicitly preauthorized stop operation or a new Plan; show pending/failed remote stops honestly. A routine's activation approval can include a narrowly scoped stop operation, never an implicit delete or edit permission.

Members and Agents may propose creating, changing, disabling, or deleting a shared household routine without the creator's permission. Only a human Owner approves the exact version, in the Owner Review Queue (W033 E2–E4); chat may notify a designated Owner and deep-link to the Console, but no chat message approves. Review, version, and safety checks still apply. Concurrent edits use the routine version and require a fresh preview when another change has landed.

Any Owner may immediately disable or revoke a specific routine/version without a Plan, in the Console or through an authenticated direct chat control, because stopping only removes effective authority (W033 E6.1). That runtime denial also creates or links the declaration-removal Plan from A7.1. Chat cannot activate, edit, delete, or approve a routine Plan.

_Changed by ADR-W033 §E2–E4, E6.1: routine approval moved from any admitted adult on a household review page to a human Owner._

## A7. Owner-controlled tools and requests for missing capabilities

Tools are Member- or Owner-class and may be marked opt-in. Owner tools are granted only to Owner Agents; an Owner grants each Agent whole service bundles or explicit tool selections (W033 B3–B5). The Console shows each Agent's grants, grouped by service and integration connection, with tool purpose, data access, mutating behavior, approval requirements, availability, grants, and dependencies.

Disabling a tool both removes its advertised specification and rejects subsequent dispatch, including from saved sessions and routine runs. Cached tool lists are not authority. In-flight effects may be irreversible; report them.

Member Agents exclude shell execution, arbitrary code, unrestricted filesystem search, credential access, and infrastructure administration. Toggles and grants cannot cross that ceiling. A read tool also needs scope: searching connected recipes differs from searching every host file.

Butler can create durable requests linked to a blocked task:
1. Enable a supported but unavailable tool with proposed scope.
2. Develop a missing capability with behavior and acceptance criteria.

An Owner may approve, narrow, or reject. Requests confer no authority. Development approval is separate from installation and enablement. Automatic tool development and self-modification are deferred.

A Task holds no grant of its own: its authority is derived from the request that created it, re-evaluated at every boundary, and never widens (W033 A0). Standing enablement is a per-Agent grant administered by an Owner. Approved routine versions hold scoped grants for their declared tools/integration connections/actions while enabled; these are not general conversational grants. All authority remains subordinate to current Agent-class ceilings, tool switches, Person admission, and revocation. _Code note: the task-bound grant records from P7 predate this rule and are not yet conformant._

### A7.1 Structural enforcement and control-plane state

Compose each Agent's gateway structurally from its class and grants. Runtime filtering only narrows it; it cannot turn a Member Agent into an Owner Agent. Use one effective-authority resolver for dispatch, applying W033 A0's three layers: general execution authority for the Person, Task, or routine version; resource authority intersecting the Agent's class and grants, Connection admission, integration-connection permission, enabled tools, action approval, and current model verdict; then disclosure to the audience and Connection. Add structural tests rejecting direct handler execution that bypasses this resolver.

Extend the existing minimal tool manifest with purpose, input schema, data/action scope, mutating behavior, and approval requirements. A declaration alone still supplies no executor. Generate the offered capability inventory and supported resource-kind enumeration from the active gateway and kind registry, with validated descriptive metadata attached there rather than a second handwritten list. Pin coverage and exclusion in tests, including ConfigFile/SeedFile proposal support and QA-only restrictions. Provide a read-only self-capability tool showing only the calling Agent's effective manifest and scoped unavailable-capability reasons, never hidden privileged tools or secrets. Consult it before filing a capability request.

For service configuration, use a ConfigFile Plan for configuration consumed from managed paths, and an authorized adapter settings action for app-owned settings. SeedFile remains write-once initialization; arbitrary edits inside application volumes are rejected. Infrastructure configuration stays Plan-mediated and excluded from household automation.

Add an Owner-class bounded container-log tool using the existing Wardstone `ContainerLogs` operation, not a new protocol arm. Preserve managed-container ownership checks, tail/byte limits, redaction and untrusted-result envelopes, and enforce current Agent-class and node scope. Member Agents never receive this tool.

Per-Agent tool grants, identity links, and Agent admission are direct Owner administration in Console/CLI, with runtime projections checked at use. Butler can propose only changes permitted by its own tools and can otherwise file a request; it cannot approve them. All disables/revocations are immediate runtime denials, including unlink, and override desired-state reconciliation: a previously approved declaration cannot silently re-enable revoked access. Re-enabling requires fresh Owner action; a revoked routine needs a new approved version (W033 E6.1). Revoking a declared standing permission also creates or links a proposal to remove that declaration; Console shows “revoked, declaration pending removal” until the human-approved cleanup completes. Failed or rejected cleanup never lifts the runtime denial. Apply normal Plan risk classification to the actual diff rather than automatically assigning every cleanup Low risk. Host state and standing routine declarations remain Plan-mediated; routine grants remain subordinate to current denials.

Chat can show a Plan ID and a validated deep link to the Console. The link carries no approval authority or bearer credential; Owner Console authentication (W033 A4, A4.1) is still required. No chat callback approves a Plan or grants administrative access.

## A8. Tool access and action approval are separate

A clear request can authorize a permitted low-impact household action. Consequential operations require approval of the exact proposal. Chat approvals of exact household actions are bound to the approving identity and proposal version, expire, and cannot execute twice from duplicate clicks. Personal changes require the Person; shared changes require a Person authorized for them. Durable automation and standing authority remain Plans approved by a human Owner (W033 E2). Effective authority intersects the Person, Agent, Connection, and Task/routine legs (W033 A0).

The default classification is criteria-based. A low-impact action is narrow, reversible, requested by the affected person, and has no financial, external-communication, access/security, physical-safety, destructive-data, or shared-schedule effect. An action is consequential when it spends or commits money, communicates externally as a person, changes access/security or a physical safety state, deletes non-reconstructable data, or changes a shared calendar/routine with effects on others. Infrastructure and permanent authority changes remain Plans in Console/CLI. Adapter metadata proposes a class, but platform policy validates it and an Owner may make it stricter, never silently weaker.

Infrastructure approval remains in Console/CLI. Enabling a tool, receiving a document, or accepting a learned procedure does not approve an action. Retrieved content is untrusted input, including email instructions and event payloads.

### A8.1 Approval transport

Do not interpret ordinary chat answers or the most recent pending question as approval. Each proposal carries a stable ID, revision, intended approver, exact action/scope, expiry, and single-use approval token. Bind callback handling to authenticated direct-message identity and consume approval atomically with dispatch authorization. Group messages cannot approve.

Telegram callbacks require an explicit adapter/API extension; the current free-text answer claim path is insufficient. A text fallback must name the exact proposal ID and revision and pass the same identity, expiry, and duplicate checks. Edits invalidate earlier tokens. Delivery acknowledgement is separate from human approval.

## A9. Model choice does not change identity or authority

Each Agent owns an ordered model/provider chain (W033 B6). There is no deployment-wide fallback order, and Wildstone never substitutes another Agent. Configure named endpoints/models and processing location for each chain entry. A remote Ollama endpoint is not proof of either local or cloud inference.

Fallback moves only along the Agent's own chain, within bounded attempts. Content whose processing policy is local-only fails rather than falling to a cloud entry. Background embeddings, extraction, and compaction prefer local processing where quality is adequate. Deterministic operations continue without models. Current code assigns one model per Agent; the ordered chain is not yet implemented.

Use configurable endpoint concurrency and interactive capacity, with lower-priority ingestion/compaction. Defer cost tracking and account-limit enforcement: returned usage metadata does not establish remaining shared provider allowance.

_Changed by ADR-W033 §B6: the model order belongs to each Agent, not the deployment._

### A9.1 Data routing and model readiness

Whether content may reach a cloud model is decided by each record's and source's processing policy, evaluated against the chain entry about to process it (W033 C11, D7); local-only sources cannot be sent there. Background processing prefers local models but may use cloud only when its own job policy and source permissions allow it. Future Child cloud routing requires an explicit guardian/administrator policy. This deliberately amends the vision's blanket family-local-only wording.

Every fallback model must pass its own capability/readiness assessment. A QA-only verdict cannot inherit the prior model's action authority. Recompute effective authority after model selection; pending writes wait for a permitted capable model or human intervention. Provider availability never widens permission.

## A10. Communication, retention, and recovery are explicit policies

Allow proactive messages, with deduplication, relevance checks, quiet hours, and appropriate Connection routing. Quiet hours use the configured household timezone and support per-person overrides; urgent exceptions require explicit designation. The owner's preferred hours are recorded as a deployment example in the brief. These are configurable policies, not special-purpose routine logic.

Task updates go to the owner, private messages stay private, and unassigned notices default to the designated Owner (W033 E3) without granting access to private content. Replies correlate to the originating question; ambiguous or expired answers do not authorize stale actions. Silence is never approval.

Back up tasks, conversations, memories, grants, mappings, routines, procedures, and access settings. Reconcile restored actions against external state before resuming. Restore into quarantine: no Butler retrieval, task dispatch, ingestion, or proactive delivery until an Owner reconciles authority and deletion state. Reapply available later deletions/revocations; an old backup cannot supply missing later decisions. Where reconciliation cannot establish current permission or deletion status, keep affected content unavailable and require fresh authorization and, where appropriate, reindex from current permitted sources. Administrative acknowledgement alone is not evidence that missing deletions were recovered. Conversation/task-summary retention defaults to manual deletion with configurable cleanup.

Offboarding records and deletion/retention deadlines are part of the authority state restored before exposure. A restored member, binding, grant, connection, or private-memory index remains quarantined when a later offboarding record may be missing. Export is a read governed by current permissions and never bypasses restore quarantine.

### A10.1 Undelivered notices and recovery evidence

Track delivery acknowledgement separately from a human response. A completed task whose notice expires remains completed, with the notice marked expired/undelivered and visible in Console; it must not become an unanswered approval wait. Waiting-for-human tasks remain waiting under their own deadline policy. No expired notice or silence approves work.

Durable Butler runtime state becomes a fourth recovery category alongside the existing recovery inputs; it is no longer wholly rebuildable. Amend W018 and the recovery guide to cover task ledgers, conversation/memory data, bindings, grants, and access controls. Replication lag is a recovery-point limit, not proof of zero loss. The recovery drill must restore an older snapshot containing subsequently revoked access/deleted content, demonstrate quarantine, and prove uncertain content and pending actions remain blocked until reconciliation.

## A11. One active coordinator, observable work

V1 runs one active Keystone/Butler coordinator and one authoritative runtime database. Do not add active-active writers, automatic leader election, or concurrent task schedulers. Recovery may prepare a standby copy, but promotion is explicit and fenced so the prior coordinator cannot continue dispatching. Adapter placement may fail over as described in A5 because adapters claim work from the active coordinator; when the coordinator is unavailable, Wildstone-owned cross-application work waits. Routines running natively in an application continue under that application's own availability.

Every Butler task produces a structured, append-only work trace that records what the system can actually observe:

- task/session/Person/Agent/Connection IDs; model endpoint and capability verdict; prompt, policy, tool-manifest, and configuration versions;
- context-source IDs, audience/permission labels, freshness, and retrieval scores without duplicating source content by default;
- proposed steps, tool calls, redacted/bounded inputs and results, attempt/lease epochs, timing, retries, fallback, stalls, waits, approvals, denials, and completion evidence;
- delivery state, user corrections, explicit feedback, cancellation, and final outcome.

Do not request or persist private chain-of-thought. A short rationale included in a user-visible proposal or answer may be stored as model-authored explanation, not as authoritative reasoning. Trace payloads pass the same redaction and permission checks as their sources; structural metadata may live with task history, while captured content inherits the strictest source retention/deletion policy. Temporary debug capture is explicit, scoped, visibly enabled, and automatically expires. Provider-reported token counts and latency may be recorded for capacity analysis but do not establish cost or remaining account allowance.

Console exposes the trace as a task timeline and supports human labels such as wrong answer, stale read, repeated work, inappropriate tool, permission refusal, excessive interruption, and useful completion. A reviewed incident can produce a sanitized regression fixture/evaluation with expected behavior. Prompt, model routing, tool metadata, policy, and evaluator versions are recorded so before/after results can be compared. Butler may recommend an improvement or file a capability request; it cannot rewrite its prompts, tools, permissions, policies, or evaluations automatically.

## B3. Alternatives and consequences

**Unrelated Agents with no shared knowledge:** rejected. The household runs several Agents (W033 B1), and continuity across them comes from Personal and Household memory while Agent-local memory stays isolated (W033 C5).

**One universal tool belt with model-selected privilege:** rejected; authority must remain outside the model and a Member Agent must not silently gain Owner tools.

**Copy every app database into RAG:** rejected; duplicates authoritative state, broadens ingestion, and hides freshness. Events, selected indexing, and live reads serve different purposes.

**Replace Wildstone with an external agent runtime:** not selected. Reuse existing policy, package, Plan, and event foundations first; an embedded/external runtime would require a separate compatibility decision.

**A new workflow broker or orchestration platform now:** deferred pending evidence that extending the runtime DB is inadequate.

The costs are durable-state complexity, permission-aware retrieval, app-specific adapter maintenance, and more recovery cases. Benefits are continuity, explainable cross-app work, reusable integration contracts, and a path to requesting capabilities without self-escalation.

### The live conversational path

`keystone/butlerlive` serves a conversation as a named Agent (ADR-W031)
over `butler.Runner` and a `butlerstore.Ledger`, and `cmd/keystone` wires it
while the process holds the coordinator lease. Concretely:

- **Which model answers comes from the Agent the message was ADDRESSED to**,
  and the address comes from the receiving bot's own Keystone credential
  rather than from anything in the request. Nothing reads the message to
  decide.
- **A conversation is a durable task.** Steps, attempts and a work trace are
  checkpointed before each dispatch, so a conversation survives a restart and
  a resumed turn serves an already-verified tool result from the ledger
  instead of dispatching it again.
- **A session is scoped to one Agent before it can run anything** — its
  authority resolver and memory scope are bound at construction, so
  isolation is structural rather than a filter that must be remembered.
- **Fallback stays within the Agent.** W033 B6 gives each Agent an ordered
  model/provider chain and never substitutes another Agent. Current code
  assigns one model, so an Agent whose model is unreachable waits.

The legacy `-butler-provider` answers only when the deployment has created
**no Agents at all**, so an upgrade does not silently go mute. That decision
reads deployment state and never message content.

Still not on the live path, and tracked separately: `keystone/adapter` behind
the integration-work queue, and `keystone/crossapp` routines run from the
automation engine.

The v1 release gate is P16, not the first successful cross-app demo. A partial deployment may dogfood P1–P5 on the existing surfaces, but memory, new connections, and new write paths remain disabled until their own package evidence and the applicable offboarding/recovery paths pass.

Follow-up work: dedicated receipt/screenshot/PDF intake, and selected read-only IMAP monitoring with review-first calendar writes. Calendar invitations/RSVPs remain separately controlled.

Voice is post-v1: local transcription preferred, Kokoro preferred for TTS, using the same identity and conversation interfaces. Cost enforcement, unrestricted execution, automatic tool development, and autonomous agent teams remain deferred.

Implementation PRs should prove:
- Same-Person, same-Agent continuity across Connections (W033 B10) without cross-audience leakage or implicit elevated execution.
- Task authority ending with the Task, tool disable, and identity revocation at dispatch, including paused/restarted work.
- A deterministic cross-app run with the model off, an unavailable source, duplicate events, and an uncertain action outcome.
- Review-bound household writes distinct from infrastructure Plan approval.
- Only a human Owner approves a routine version; mixed/infrastructure/authority Plans and all chat approval attempts are refused; any Owner's stop takes effect immediately.
- Memory correction/deletion propagated to retrieval and derived content, including restoration behavior.
- Adapter behavior against fakes and a limited real deployment, not merely a declaration that lints.
- Adapter failover only among approved nodes, single-epoch fencing against duplicate work/late results, waiting with no eligible node, and verified credential erasure/revocation when a fallback is removed.
- Offboarding immediately denies access across Connections and nodes, pauses personal work, keeps Household routines running with authorship intact (pausing only those that deliver to the departed Person or need an admission only they held), quarantines private data through retention/deletion, and survives restoration of an older snapshot.
- A trace can explain a resumed or failed task from request through retrievals, tool attempts, policy decisions, approvals, delivery, and evidence without exposing secrets, unauthorized content, or private chain-of-thought; a sanitized failure becomes a version-pinned regression evaluation.
- Starting a second coordinator cannot dispatch concurrently; explicit standby promotion fences the previous coordinator, and cross-app work waits safely during coordinator unavailability.

The accompanying brief provides non-normative rationale, deployment examples, and delivery sequencing. This ADR defines the architectural contract, governed by ADR-W033 where they overlap.
